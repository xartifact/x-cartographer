# Specification: AI 执行生命周期监控

## Feature Description

用户需要对 AI 代码执行任务进行完整的生命周期监控。当前系统只记录最终结果（完成或失败），但缺少对执行过程的全面追踪：状态模型不完整（无法区分用户取消、系统超时、正常失败）、运行中输出仅在内存中（服务崩溃丢失）、没有状态变更审计记录、缺少聚合监控指标（成功率、耗时趋势等），以及异常场景下的恢复能力不足。

本特性将建立完整的执行生命周期追踪体系：从执行创建到最终结束的每一个状态转换都被可靠记录，运行时输出在崩溃后可恢复，用户可以通过监控仪表盘了解执行系统的整体健康状况，并在各种异常场景（网络断开、服务崩溃、用户取消）下获得一致且可靠的行为。

## User Scenarios

### Scenario 1: 用户停止执行后查看准确状态

**Given** 一个 AI 执行任务正在运行中
**When** 用户点击"停止"按钮主动取消执行
**Then** 执行记录的状态显示为"已取消"（而非"失败"），用户能区分主动取消和意外失败

### Scenario 2: 执行超时后查看准确状态

**Given** 一个 AI 执行任务正在运行中
**When** 执行超过配置的超时时间（默认 5 分钟）
**Then** 执行记录的状态显示为"超时"（而非"失败"），并记录超时时长

### Scenario 3: 服务崩溃后恢复执行输出

**Given** 一个 AI 执行任务正在运行并已产生 200 行输出
**When** 服务端意外崩溃并重启
**Then** 用户在执行历史中仍能看到崩溃前已产生的输出内容（至少部分恢复），执行状态显示为"中断"

### Scenario 4: 查看执行的完整状态变更时间线

**Given** 一个已完成的执行记录
**When** 用户打开该执行的详情
**Then** 能看到完整的状态变更时间线（创建 → 运行中 → 完成），包括每次转换的时间戳和原因

### Scenario 5: 查看执行系统的健康概览

**Given** 系统中已有多次执行记录
**When** 用户打开监控仪表盘
**Then** 能看到关键指标：成功率、平均耗时、失败分类分布、最近执行趋势

### Scenario 6: SSE 断连后自动恢复

**Given** 用户正在查看正在运行的执行输出
**When** 网络短暂断开后恢复
**Then** 前端自动重连 SSE，从断点续传输出内容，用户不会遗漏任何输出行

### Scenario 7: 查看特定任务的所有执行历史

**Given** 一个任务已被执行过多次
**When** 用户查看该任务的执行历史
**Then** 能看到所有执行记录（按时间倒序），支持按状态过滤、按时间范围筛选

## Functional Requirements

### 状态模型完善

- **FR-001**: 执行状态集合 MUST 扩展为：`pending`（已创建待启动）、`running`（执行中）、`completed`（成功完成）、`failed`（执行错误）、`cancelled`（用户主动取消）、`timed_out`（超时终止）、`interrupted`（服务崩溃中断）
- **FR-002**: 状态转换 MUST 遵循明确的有限状态机规则，非法状态转换 MUST 被拒绝并记录警告
- **FR-003**: 用户主动停止执行时，系统 MUST 将状态设置为 `cancelled` 而非 `failed`，停止操作 MUST 等待服务端确认后再更新前端状态
- **FR-004**: 执行超时时，系统 MUST 将状态设置为 `timed_out` 而非 `failed`
- **FR-005**: 服务重启时发现的 `running` 状态记录 MUST 被标记为 `interrupted` 而非 `failed`

### 输出持久化

- **FR-006**: 执行运行期间，输出内容 MUST 定期增量持久化到数据库，而非仅在执行结束时一次性写入
- **FR-007**: 增量持久化 MUST 不阻塞 SSE 实时推送，写入操作 SHOULD 异步进行
- **FR-008**: 增量持久化失败时 SHOULD 重试，且不影响执行本身的运行

### 状态变更审计

- **FR-009**: 每次执行状态变更 MUST 记录到审计日志，包含：来源状态、目标状态、变更时间、变更原因、可选的附加元数据
- **FR-010**: 审计日志 MUST 支持按执行 ID 查询完整的状态变更历史

### 持久化可靠性

- **FR-011**: 执行完成后的数据库持久化 MUST 使用持久化队列机制，确保即使首次写入失败也能在后续重试中完成
- **FR-012**: 内存中的执行历史缓存 MUST 有容量上限，超出时按 LRU 策略清除最早的记录

### 异常恢复

- **FR-013**: 前端 SSE 连接断开时 MUST 自动重连，使用指数退避策略（初始 1 秒，最大 30 秒），重连后 MUST 从服务端获取断连期间的输出
- **FR-014**: 前端 SSE 重连时，服务端 MUST 支持从指定输出行索引开始发送，避免重复传输

### 监控仪表盘

- **FR-015**: 系统 MUST 提供执行监控仪表盘，展示关键指标：成功率、平均耗时、失败/取消/超时分布
- **FR-016**: 仪表盘数据 SHOULD 支持按时间范围筛选（最近 24 小时、7 天、30 天）

### 查询能力增强

- **FR-017**: 执行历史查询 API MUST 支持按状态过滤（可多选）、按时间范围筛选、分页（offset + limit）
- **FR-018**: 执行历史查询 API SHOULD 暴露已有的 `findByStatus` 能力

## Success Criteria

- **SC-001**: 用户主动停止的执行在 UI 中显示为"已取消"状态
- **SC-002**: 超时的执行在 UI 中显示为"超时"状态
- **SC-003**: 服务崩溃重启后，被中断的执行显示为"中断"状态，且崩溃前的输出可查看
- **SC-004**: 任意执行记录可查看完整的状态变更时间线（含时间戳）
- **SC-005**: 监控仪表盘正确显示成功率、平均耗时、失败分类等聚合指标
- **SC-006**: SSE 断连后 10 秒内自动重连并恢复输出流
- **SC-007**: 执行历史支持按状态过滤和时间范围筛选
- **SC-008**: 执行运行期间的输出在服务崩溃场景下至少保留崩溃前最近一次增量写入的内容

## Key Entities

- Execution（执行记录）
- ExecutionStatusHistory（执行状态变更审计日志）
- ExecutionOutput（执行输出分块）
- ExecutionMetrics（执行聚合指标）

## Edge Cases

- 状态转换冲突：超时和用户取消几乎同时发生时，以先到的转换为准
- 输出增量写入与最终写入重叠：使用 chunk index 保证幂等性
- PGlite 在高频增量写入下的性能：需要合理的 batch 大小和写入频率
- 服务崩溃时正在进行增量写入的事务：下次启动时通过 cleanup 处理
- 长时间运行的执行（数小时）产生大量输出：输出分块存储，前端按需加载
- 同一任务多次执行的历史查询性能：需要索引支持
- 内存历史缓存 LRU 淘汰时正好有 SSE 订阅者在读取：淘汰操作不影响活跃订阅

## Clarified Decisions

- 增量输出持久化频率：每 100 行 flush 一次，或每 10 秒定时 flush（以先到为准）。崩溃时最多丢失 100 行或 10 秒内的输出，数据库写入压力较低。
