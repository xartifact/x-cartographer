# X-Cartographer — AI-Native 产品方法论

> 状态：**草案，待确认（2026-09-04）**。本文档回答"为什么这样设计"，与 `x-cartographer-architecture.md`（"现在长什么样"）互补，不重复其内容。所有引用均来自当前 `feat/core` 分支的真实代码/文档，非推测。

## 0. 前提：两个一等公民用户

X-Cartographer 的用户不是"人类，外加一个 API 给 Agent 用"，而是**AI Agent（自主研发循环）与人类，同为一等公民**。任何交互形态、数据关系的设计，都必须同时回答：

- 这对正在跑 loop 的 Agent 意味着什么（它能不能在一次调用里拿到需要的信息、能不能不看 UI 就完成操作）？
- 这对人类意味着什么（能不能看懂、能不能审阅/干预）？

默认往"人类 UI 直觉"上靠是错误的起点——本仓库过去已经吃过这个亏（见 §2 反例）。

## 1. 核心立场：纯协调层，智能在 Agent 一侧

这不是本文档新定义的立场，是已经被代码和文档反复确认、且被强制执行的既有决策：

- `README.md:122`："X-Cartographer 是**纯存储与协调层**，**不内置任何 LLM/AI 处理能力**。智能…由**外部 Agent** 通过 `xcart` CLI + Skills 驱动"。
- `AGENTS.md`（开发约束段）："**禁内置 LLM 依赖**：项目定位为纯存储/协调层（`refactor: remove built-in AI`）。story/任务 AI 生成类需求按架构决策废弃，勿新建该类功能。MCP Server 已评估并否决，不实现。"
- `apps/server/src/routes/settings.ts:2`（代码注释，最精确的一句表达）："内置 LLM 配置（/llm/\*）已随'移除内置 AI'移除，**智能交由外部 Agent 驱动**。"

**推论：任何"质量/合规/正确性"判断都不能设计成服务端逻辑，只能是 Agent 自证、服务端记录。** 这条推论是本文档五项原则里 P3 的直接来源，也是评估"技术宪法"这类新功能时最先要过的一道闸门。

## 2. 反例：`tech_stack` 孤儿字段

`Project.metadata.tech_stack: string[]` 是本仓库里"设计了数据、没设计消费者"的真实案例：字段存在、可在 Web UI 编辑，但从未被 `xcart overview`、`xcart context export` 或任何 SKILL.md 读取或展示——它原本是喂给已下线的内置 LLM 拆解功能的输入，功能下线后，字段变成死数据。**这是本文档 P2 的实证依据，也是后续任何新字段上线的反面教材。**

## 3. 五条原则

### P1 — 一个规范模型，多个投影；投影形态跟数据本质走，不跟"统一 UI 约定"走

`packages/shared` 是唯一类型事实源（`docs/design/x-cartographer-architecture.md:48`），REST/CLI JSON 是 Agent 投影，Web SPA 是人类投影——但**不代表两个投影长得必须一样，也不代表人类投影内部所有场景都套同一个组件**。

`AGENTS.md`："详情交互统一用 `Sheet` 抽屉" 是一条好的默认约定，但它的适用范围是"集合里的一条记录的详情"（一个任务、一个故事）。当数据是"这个项目唯一的一份文档"（例如整份技术宪法），Sheet 不是正确投影——应该是独立页面；而这份文档的某一次历史修订快照，回到了"列表里的一条记录"形态，才该用 Sheet。

**如何应用**：新功能设计时先分类——"这是集合里的一条记录，还是这个实体唯一的一份配置/文档？"——再决定用 Sheet 还是页面，不要不假思索套用"统一 Sheet"。

### P2 — 上下文是被设计出来的产物，不是存储的副产品

数据"存在于数据库"不等于 Agent"看得到"。真正决定 Agent 能否用上一个字段的，是它有没有出现在 `overview` / `context export` / SKILL.md 里——这三者才是 Agent 的实际输入面。

同一个原则也约束着人类投影：`AGENTS.md`（API 数据流约束）："深树一次取全…**勿**逐 story 拉 `task list` 凑数（有 N+1 前科）"。这条防 N+1 的工程规则背后是同一件事——**数据要以"消费者一次能吃下"的形态交付，不管消费者是 Agent 的 context window 还是浏览器的一次渲染**。

**如何应用**：新字段/新实体上线时，必须在**同一个变更**里接入至少一个 Agent 可读的输出面（CLI `--format json` 字段、SKILL.md 的读取步骤、或 `context export`）。"先建模型，Agent 读取以后再补"默认视为不合格设计——`tech_stack` 就是"以后再补"从未发生的真实案例。

### P3 — 声明式约束 + 自证，而非集中裁决

见 §1 推论。任何"合规/质量/正确性"相关的新能力，第一个问题永远是"谁来判断对不对"——答案必须是"外部 Agent"，服务端角色永远止步于"记录这份判断、检查它形状是否完整"，不能演变成执行代码或语义裁决。

**如何应用**：设计校验逻辑时反复自问——这是在检查"字段齐不齐 / 值合不合法的结构性检查"，还是在判断"这段代码/这次实现对不对"？前者允许放在服务端，后者永远不允许。

### P4 — 每次变更可追溯、有理由，新治理机制复用同一本账本

`--reason` 在状态流转上强制要求、`status_changes` 表记录"谁在何时把什么改成了什么"——这是一套已经存在的"仅追加事件日志"模式，本质是给人类和 Agent 共同信任的审计轨道。

**如何应用**：任何"会演进"的实体（例如会随里程碑变化的配置/规范），新版本历史应延续 `status_changes` 的语义——谁、何时、为什么变了——而不是发明一套平行的、语义不一致的版本机制。

### P5 — 交互形态跟随"今天真实可用的通道"，不跟随架构图上的愿景

MCP Server 已评估并**否决**（最终裁决，不再是"规划中"或"待确认"）。Agent 侧唯一真实可用的通道是 shell 调用 `xcart` CLI（文本/JSON 输出）+ SKILL.md（自然语言指令）。

**如何应用**：设计 Agent 可用性时，验收标准是"CLI 有命令 + `--format json` 有稳定字段 + SKILL.md 教会怎么用"，不是"某个通道理论上支持"。不要为未落地的通道预留设计余量。

## 4. 这份文档怎么用

任何新功能设计——包括正在暂停、等待这份文档定稿的"技术宪法"方案——在写代码前先过一遍 P1–P5 自检。出现原则与具体设计冲突时，是原则该修，还是设计该改，必须显式讨论，不能悄悄绕过。
