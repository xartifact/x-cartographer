# 1.0 之后：产品、系统、工程三视图与交付追溯

> 状态：设计提案，已获授权登记为 1.0 之后需求；不是已接受的架构决定，也不是实施授权。
> 日期：2026-09-20。产品：实时网关的 `X-Cartographer-Dev / PROD-005`。
> 需求池：`MS-025`（v1.0 之后，待排期）；现有 v1.0 `MS-003` 范围不变。
> 设计登记工作：`TASK-616`；入口故事：`US-232`。

## 1. 产品定位与设计依据

产品首先描述需求，其次约束实现；主要读写对象是外部 Agent，人能够理解、审计与干预。覆盖纯软件及硬件、固件、App、云端组成的完整产品。

用户已主张的范围：三个视图协作，UI/UX 行为设计，Bug 与问题追溯，版本管理与分发。以下实体划分、状态及切片是 Agent 设计提案，来源为 `agent_inferred`，不能因用户授权登记而变成 `human_asserted` 或已接受 ADR。

依据：[领域模型](domain-model.md)、[故事地图语义](story-map-redesign.md)、[AI-Native 原则](ai-native-product-principles.md)、[技术宪法](technical-constitution.md)。现有代码与实时任务板优先用于判断已实现能力；历史文档中的未实现标记不能直接沿用。

系统工程参考：[NASA 系统设计过程](https://www.nasa.gov/reference/4-0-system-design-processes/)。借鉴迭代需求定义、逻辑分解和验证，不将其转写为强制十二阶段流程，也不承诺标准认证。

## 2. 设计结论与范围

1. 保留约束 / 工作 / 证据空间，用于规定写入语义；产品 / 系统 / 工程是读取与操作投影，不是新的域隔离墙。
2. 三视图共享实体身份与修订；导航切换不复制需求，不创建镜像数据。
3. 故事地图表达用户价值与交付切片；场景表达行为；要求表达可验证义务；系统组成与接口表达实现责任；任务表达行动；证据表达发生过什么。
4. 系统能力是可选组织层。简单软件故事可以直接关联场景或要求，不强制补齐所有中间节点。
5. 每个切片必须同时具备 CLI JSON、上下文消费、最小人类审计入口和验证案例，不能先造无人读取的 schema。
6. 不内置 LLM、不建设 MCP Server，不执行 CI/CD、CAD、仿真或设备控制；保存外部工具的引用、结果与依据。

不在本轮范围：完整 SysML/MBSE 编辑器、CAD/BOM 全生命周期管理、制造采购库存、设备资产管理平台、权限体系重建、自动安全认证、强制所有变更人工审批、任意类型的通用图数据库产品。

## 3. 三个视图的职责

| 视图 | 面向 Agent 的问题 | 面向人的审计入口 |
|---|---|---|
| 产品 | 为谁达成什么目标，本次范围是什么 | 故事地图、用户场景、发布范围、体验承诺是否有依据 |
| 系统 | 系统边界是什么，怎样表现，谁承担什么 | 能力、要求、组成、分配矩阵、接口、ADR、待决定问题 |
| 工程 | 怎样实施，验证了什么，交付了哪个配置 | 任务、问题、验证运行、发行配置、分发结果 |

系统架构的结构事实归系统视图；工程视图引用相同组成节点，展示其工程资源与交付事实。避免再建一棵 HW/FW/App/Cloud 架构树。

## 4. 概念模型与最小边界

| 概念 | 语义与必要信息 | 空间与版本规则 |
|---|---|---|
| Product / Activity / UserTask / Story | 沿用用户目标、叙事流、操作步骤与交付切片 | 约束；保留现有 ID 与地图语义 |
| Capability | 系统能做什么，边界与目标；与 Story 多对多 | 约束；可选，不等于组件或页面 |
| Scenario | 前置条件、触发、参与者、步骤、可观察结果、异常分支、未决项 | 约束；稳定步骤 ID、内容修订 |
| Requirement | 条件、主体、义务、判据、来源、适用范围、验证方法 | 约束；不可变修订，功能/质量/交互等为分类 |
| SystemModule 的演进 | 系统组成、类别、父组成、边界、职责、工程资源 | 约束；沿用产品内身份，新增修订与设计/实际区分 |
| Allocation | 某要求由某组成承担的具体职责、范围与理由 | 约束关系；可以多对多，不等于 affected_modules |
| InterfaceContract | 参与方、输入输出、协议或物理约定、时序、错误、兼容性 | 约束；绑定准确修订与组成端点 |
| ADR | 为何选择该方案、替代方案和后果 | 沿用决策账本，引用上述对象，不重复定义 |
| DevTask | 实施、调查、验证或治理行动 | 工作；可引用要求、接口、问题，保留现有故事/模块锚定 |
| Issue | 待解释的现象或风险，当前调查结论与处置 | 工作；原始报告、观察与结论修订在证据中追加保存 |
| VerificationSpec / VerificationRun | 怎样验证 / 实际验证了什么 | 前者为约束，后者为证据，二者分离 |
| DesignBaseline | 显式选定的一组需求、组成、接口、ADR 修订 | 约束；冻结后只新增基线，不覆写 |
| ReleaseConfiguration | 实际发行的组件版本、工程产物和适用配置清单 | 草稿属工作；封存的 manifest 属证据 |
| DistributionRecord | 在指定目标上实际分发了哪个配置，结果如何 | 意图可用 DevTask；结果与后续更正追加记录 |

这些是逻辑概念，不等于立即建立同样数量的数据表。明确消费者、查询及修订语义后再定物理 schema。

### 4.1 需求与验收条件不重复维护

单故事局部且不需要独立修订的验收条件保留在 Story。跨故事复用、需要责任分配或独立验证的内容提升为 Requirement，原故事引用它。提升操作保留来源，不复制两份可编辑正文。

要求来源可为用户故事、场景、外部规范、接口兼容、环境条件或风险分析。缺失来源显式显示“待补充”，不得为满足链路完整度而伪造用户故事。外部规范记录准确版本与引用位置。

“响应快”是目标而非可验证要求。性能要求必须定义触发点、结束点、测试条件、单位、阈值与必要的统计口径；未知数值使用待决定标记，Agent 不代填产品承诺。

### 4.2 系统组成不再假设等于代码目录

扩展现有 SystemModule，支持 system/subsystem/hardware/firmware/software/external 等类别，路径改为工程资源的一种。沿用 `(product_id, module_id)` 身份，不创建与旧模块目录并行的权威表。

组成树表达 part-of；依赖、通信、责任分配各有语义。计划中的组成与某发行配置中实际存在的组成分别展示。外部系统须标明边界与依赖假设，不能分配内部任务后就暗示拥有控制权。

### 4.3 UI/UX 是场景的体验约束

黑盒场景先描述对外行为；方案确定后，内部交互关联同一场景的步骤与分支，不覆盖黑盒承诺。交互规格记录屏幕、按键、灯光、声音、无障碍、等待、失败、恢复等用户可观察规则。

交互规格首期可作为带修订的场景内容与要求引用，不独立建设设计资产平台。原型/截图标明“参考示例”或“必须遵守”的性质及来源；关键行为必须有文本契约，不能只留图片。

例如开门：发送命令成功、执行机构动作、传感器确认打开是不同事实；“已打开”反馈绑定哪个事实必须可审计。超时后的实际状态可能未知，不允许简单把所有失败映射为“门仍关闭”。

## 5. 追溯关系与约束生命周期

| 关系 | 表达什么 | 禁止误读 |
|---|---|---|
| Story ↔ Scenario / Capability | 用户目标由哪些行为或能力支撑 | 关联不证明已实现 |
| Requirement derives_from 来源 | 要求为何存在 | 不能强制全部来自 Story |
| Requirement allocated_to 组成 | 谁承担哪部分责任 | affected_modules 只是影响面 |
| ScenarioStep uses InterfaceRevision | 场景中的协作依据 | 提案接口不自动成为已生效契约 |
| Task addresses Requirement / Issue | 本次行动针对什么 | 完成任务不自动满足要求或关闭问题 |
| VerificationRun checks 修订与配置 | 证据适用于什么条件 | 旧修订通过不代表新修订通过 |
| ReleaseConfiguration contains 产物 | 实际发行了什么 | Milestone 计划不是发行清单 |

关系有单一存储方向和反向查询投影，不能为了双向导航保存两份权威引用。组成、派生和任务依赖分别检查无环；通信允许双向，不能把整张追溯网强制变成 DAG。

初期采用有限关系类型及端点校验，不开放任意边类型。关系本身记录理由、来源和适用修订；删除用归档/墓碑保留历史链，既有悬空引用只报告，迁移中不悄悄清除。

新约束的修订需要区分草稿、已采用、被替代/撤回。`provenance`、是否采用、是否满足、是否已交付是不同维度，不能再压成一个 status。现有 Story.status 及 accepted 语义需在迁移设计中明确映射，不批量重解释存量数据。

采用新修订是显式动作，带操作者、理由与依据；本提案不新增全局人工审批门禁或角色权限模型。任务执行不能顺带改写有效约束。尚待决定的要求进入上下文的未决区，不作为已承诺的实现前提。

## 6. 修订、基线与影响复核

逻辑 ID 表示同一对象，revision ID 标识不可变内容。草稿可修改，采用后内容冻结，新修改产生新修订。更新采用 expected_revision/CAS 防止并发覆盖；复杂图批量写入有事务或明确部分成功结果与幂等键。

设计基线显式列出对象修订、关系及适用配置，不能通过“截至某日期取当前模块目录”伪造历史。形成基线前报告缺失项，保留 unresolved；服务端可以检查引用与清单完整性，不能声称已经判断工程正确性。

要求/接口变化后，从已登记关系计算“候选受影响对象”。相关证据保持原记录，只在当前视图标记待复核，不修改原验证结果。Agent/人追加适用性结论及理由，决定复测、继续适用或不适用。图上未连接不等于没有影响，应同时报告覆盖缺口。

复用 status_changes 的操作者、时间、理由与追加原则，但它只有状态转移字段，不能充当完整测试结果或内容快照。专用证据记录通过统一审计查询被浏览，不把所有内容塞入 reason，也不比较两张表的独立 seq 推断全局先后。

## 7. 问题、Bug 与验证

Issue 先记录症状、发生配置、环境、复现步骤与原始证据。调查时分别记录观察、假设、确认结论。Bug 是“已确认偏离某个预期”的分类；预期未定义时标为需求歧义，不让 Agent 凭空补出要求。

建议生命周期：open → investigating → resolved → closed；closed 可以显式 reopen。分类、严重度、修复优先级与生命周期独立。duplicate / cannot_reproduce / not_a_bug 等作为处置结论，均保留理由与证据，不要求一律修代码。

修复任务完成只说明工作完成。Issue 详情分别呈现修复、验证、进入发行配置、到达目标环境四项事实。关闭结论说明适用配置与范围；未覆盖其他硬件修订时不能显示“全量解决”。

VerificationSpec 描述测试/分析/检查/演示的方法与判据。VerificationRun 保存目标修订、被测配置、设备/环境、执行者/工具、时间、结果、附件引用及可用的摘要校验值。通过、失败、受阻、未执行与未知清楚区分。

人/Agent 的符合性判断必须引用证据，原始仪器输出与分析报告区分。产品目标的场景确认与逐条要求验证分别展示。外部证据不可访问时显示不可访问，不伪装为已核验；失效链接有可见缺口。

## 8. 版本、配置与分发

Milestone 仍是可变发布目标和范围，不转成配置清单。ReleaseConfiguration 记录硬件修订、固件/App/云端版本、协议版本、产物 URI/摘要、目标型号、已知问题、验证及基线引用。纯软件产品只填实际存在的组成。

标明兼容声明是已验证、声明支持或未知，并附条件与依据。版本号排序不等于兼容关系。不能要求整个系统共享一个 SemVer，也不能因某组件升级就自动认定整个系统组合有效。

发行清单可先为草稿，封存后不可覆写；发现错误通过更正/替代记录保留原事实。分发记录区分计划目标与实际观测结果，记录环境/渠道/设备群外部标识、目标配置、实际配置和失败原因。

外部 Agent/CI 执行分发，xcart 仅协调与留证。部分成功必须可表达，计划分发不改变“当前运行版本”。回滚是新的行动与结果，并受配置兼容和不可逆迁移条件约束，不能假定所有硬件/固件都可回滚。

## 9. Agent 操作协议与人的交互

### 9.1 Agent 消费契约

扩展现有 ctx / trace / context export，不新建平行上下文系统。结果至少包括：意图、适用要求与修订、场景、职责、接口、ADR、目标配置、关联问题、预期验证、未决项，以及每一项被纳入的关系路径/理由。

提供摘要与可继续读取的明细，标明截断/游标/缺失，不能静默丢弃约束。缺失关联不等于不适用；显式不适用带理由。输出有 schema version，API/CLI JSON 键统一 snake_case。每条写入可回读、可幂等重试；用户输入与外部证据内容不成为 Agent 操作指令。

### 9.2 人的审计交互

三工作区共用产品、基线/发行配置和当前对象上下文。跨视图跳转保留筛选、选择和返回位置，链接可直达对象的准确修订。

集合对象详情使用现有 Sheet；完整流程/分配矩阵为独立页面。默认展示当前问题所需内容，按需展开跨视图对照，不默认强制三栏。

关键入口：

- 故事详情：用户承诺、关联场景/要求、交付与验证依据。
- 要求详情：来源、准确修订、责任分配、验证状态、变更影响。
- 场景详情：正常/异常步骤、交互反馈、内部协作、未决问题。
- 问题详情：原始现象、配置、调查、修复、复测、发行和分发去向。
- 发行详情：计划与实际差异、组件组合、兼容依据、未解决问题、目标环境结果。

必须区分“未关联 / 未验证 / 验证失败 / 待复核 / 不适用”。关联覆盖率不作为满足率，任务进度不作为产品验证结论。冲突与缺失首先显示可定位原因及下一步，而非只有红绿百分比。

## 10. 两条贯穿验收案例

### 软件案例：调整故事的发布归属

故事表达调整交付范围，场景覆盖成功、失败、并发冲突。交互区分保存中、已保存、未知结果与冲突处理。要求描述数据一致性和恢复结果；模块分配到 Web/Gateway/持久化；接口约定冲突响应。Agent 取得准确约束，提交验证；发行清单固定实际包含的变更。后续故事移到其他 Milestone 不改变历史交付记录。

### 软硬件案例：离线手机开门

故事表达断网条件下完成开门。黑盒场景覆盖授权失败、通信断开、机械卡阻和状态未知；实际时延与功耗指标待产品输入，不编造数值。要求分配到 App/固件/执行器/传感器，接口表达重试与状态确认。验证绑定硬件修订和固件组合；Issue 记录仅特定组合复现的问题；修复配置与目标设备群分发结果分别可追溯。

通用验收：两案例都可经 CLI 建立/读取并通过 Web 审计；软件案例无需构造虚假硬件节点。此为未来验收计划，本次未运行功能验收。

## 11. 与现有设计的差异及兼容策略

| 现有事实/规则 | 本提案的改动 | 迁移边界 |
|---|---|---|
| SystemModule 为代码结构目录，无内容修订 | 扩展到系统组成与修订 | 保留 ID；不复制新权威目录，不伪造历史 |
| affected_modules 仅影响标注 | 增加具体责任分配 | 旧数组不自动升级为 Allocation |
| ADR 的模块定义已移除 | ADR 仍解释决策，引用组成修订 | 不恢复 changes.modules |
| 技术宪法 §2 排除自证/复核 | 新增独立验证证据能力 | 显式范围扩展；不加入任务完成强制裁决 |
| 所有约束边统一无环 | 按关系类型限制环 | 单权威方向继续保留 |
| Story.accepted 混有历史验收含义 | 拆开采用、满足、交付维度 | 历史标记保留，不自动证明验证通过 |
| 非 ADR 高影响写入直接生效并留账 | 新对象修订的采用规则需明确定义 | 本轮 backlog 登记不引入 proposed 新枚举 |
| StatusChange 只存状态转移 | 验证/内容修订专用记录，统一审计入口 | 不改写证据，不把 reason 当快照 |
| Milestone 是计划范围 | 新增实际发行配置与分发记录 | 既有版本不自动宣称已发布 |

实施前需形成针对这些差异的明确 ADR；本文件不修改现行权威规则。迁移采用扩展→消费者接入→回填可确认信息→验证→弃用的顺序。旧故事和旧 CLI 能继续工作；无法确认的历史记 unknown。

## 12. 交付切片与依赖

| 切片 | 可验收结果 | 顺序与边界 |
|---|---|---|
| A 最小三视图闭环 | 一条故事关联场景、要求、组成与接口，Agent 获取上下文，人能审计 | 首先实现来源/修订/关系基础；Capability 可在骨架后深化 |

## 13. 需要在实施设计时收敛的事项

- 逻辑概念的物理存储与有限关系集合；修订、采用、历史 accepted 的兼容映射。
- 场景内容编辑形式与局部交互规格抽取条件；首版不做内置画布。
- 外部证据保留方式、可访问性与摘要校验能力；首版默认引用，不能承诺长期外部可用。
- 配置兼容声明的表达能力与设备群外部标识；首版避免制造/库存系统范围。
- 对大产品上下文的裁剪、分页与完整性提示；不得以 token 预算为由静默省略约束。

上述未知不影响登记用户需求，但必须在对应实施任务就绪前收敛。安全、合规等具体要求由产品提供依据，本提案不替代专业验证。
