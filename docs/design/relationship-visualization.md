# X-Cartographer — 关系可视化设计（任务依赖图 / 模块归属矩阵 / ADR 演进时间线）

> 状态：**设计定稿，待实现（2026-09-08；2026-09-15 依赖更新）**。遵循 `docs/design/ai-native-product-principles.md` P1（一个规范模型，多个投影，投影形态跟数据本质走）。与技术宪法（`technical-constitution.md`）、并发修复（`task-claim-concurrency.md`）为正交设计，可独立排期；但 **§4 模块归属矩阵依赖 `domain-model.md` §6.4 的 `SystemModule` 落表**——该实体目前无表，故 §4 不可先行实现。

## 1. 背景

任务规模增长后，人类难以从列表/看板视角看清任务之间的关系——但"关系"在这个系统里不是单一概念。核对代码发现两个基础事实：

1. `apps/web/src/features/story-map/components/story-map-canvas.tsx` 里，故事地图画布旧的 `@xyflow/react` 边（edge）**只是布局边**（journey 标题→故事、故事→下一个故事的排序连线），不是语义关系——`DevTask.dependencies: string[]` 这个真正的依赖关系数据，长期未被可视化。（注：该画布已于 2026-09 被 `patron-canvas.tsx` 取代，本文档 §3 的 DAG 视图已在 `task-dependency-graph.tsx` 落地并接入任务页。）
2. `apps/web/package.json` 已声明依赖 `@dagrejs/dagre` 但全仓库零 `import` ——**孤儿依赖**，与 `Project.metadata.tech_stack` 是同一类问题（P2 教训：东西存在不等于被使用）。本设计的任务依赖图部分是"终于启用"而非"引入新依赖"。

## 2. 核心原则：一张大图装不下所有关系

系统里至少有三种结构性质完全不同的关系，硬塞进一张 node-link 图会在规模变大后产生图可视化里的经典失败模式——"毛线球"（hairball）：连线互相遮挡，比列表视图更难读。三种关系分别对应三种独立的可视化组件，不共享同一个渲染器：

| 关系 | 数据来源 | 结构形态 | 可视化 |
|---|---|---|---|
| Task ↔ Task 依赖 | `Task.dependencies: string[]` | 有向无环图（DAG） | §3 分层 DAG 视图 |
| Story/Task ↔ SystemModule | `affected_modules`（技术宪法方案新增） | 二部图（多对多） | §4 矩阵/热力图 |
| ADR 演进（supersedes） | `AdrRecord.supersedes` + `milestone_id` | 线性链/时间线 | §5 时间线 |

Journey→Story→Task 的包含关系、Story→Milestone 的分配关系，已经分别由现有的故事地图画布和排期泳道视图承载，本设计不重复处理。

## 3. Task 依赖图：分层 DAG，限定范围

### 3.1 为什么是分层布局，不是力导向布局

`Task.dependencies` 天然是有向无环图——"谁阻塞谁"有明确方向性。力导向布局（force-directed，多数图库的默认效果）优化的是"视觉上不重叠"，不保留拓扑顺序，节点位置在每次渲染时可能变化，人类看不出"这是第几层依赖"。分层布局（Sugiyama-style：按拓扑层级从左到右或从上到下排列，同层节点对齐）直接呈现依赖的先后顺序，这正是任务管理场景要问的问题——"完成 A 之后我才能做什么"。

`@dagrejs/dagre` 就是做分层布局的标准库，`@xyflow/react` 官方文档本身推荐用它做自动布局（xyflow 只管渲染 node/edge，不管布局算法，dagre 补上这一环）——这不是我们的选择，是这两个库的既定分工。

### 3.2 范围限定：绝不一次性渲染全项目

152 个任务的全量依赖图即便用分层布局也会难以阅读。默认视图必须限定范围，二选一（可都提供，用户切换）：

- **按故事/按里程碑限定**：只渲染这个范围内的任务及其相互依赖，符合"故事→任务"已有的自然分组。
- **以选中任务为中心展开 N 跳邻域**：默认 1 跳（直接上游阻塞者 + 直接下游被阻塞者），可交互式展开更多层。这与 `xcart task next` 已经在做的"只看拓扑就绪的任务"是同一个"缩小到当前相关范围"的思路，不是新发明的交互模式。

跨范围的依赖（比如 A 故事的任务依赖 B 故事的任务）用一个截断节点表示（"+ 2 个外部依赖，点击展开"），不强行把两个范围合并渲染。

### 3.3 落点

新增 `apps/web/src/features/task-graph/` 目录（同级于 `story-map`），复用 `@xyflow/react` 的 node/edge 渲染层与已有的 `zoom-controls.tsx` 模式，新增 `use-dagre-layout.ts` hook 封装 dagre 布局计算（输入 `{nodes, edges}`，输出带 `position` 的 nodes，是纯函数，不涉及组件状态）。数据源：现有 `GET /api/tasks?storyId=` 或项目全量任务树（`GET /api/projects/:id`）已含 `dependencies` 字段，无需新增后端接口。

## 4. 模块归属矩阵：Story/Task × SystemModule

### 4.1 为什么是矩阵，不是图

多对多关系（一个模块被多个故事触及、一个故事触及多个模块）用节点连线表示，连线数量是二部图两侧规模的乘积级增长，很快变得比列表更难读。矩阵（行=故事或任务，列=模块，单元格标记"是否触及"）是多对多关系的标准可视化——一眼看出"这个模块被谁触及"（看一列）和"这个故事touches 哪些模块"（看一行），且规模增长时是线性可滚动的表格，不是指数级混乱的连线。

### 4.2 用途

这个矩阵直接服务于技术宪法方案的一个实际问题：评估"改动某个模块会影响哪些故事/任务"（架构影响面），或者反过来"这个故事涉及的模块，有哪些架构原则需要遵守"（`technical-constitution.md` §4 的 `resolveEffectiveArchitectureContext` 算法，本矩阵是它的人类可读投影）。

### 4.3 落点

新增 `apps/web/src/features/module-matrix/` 目录。不需要图形库——一个原生 HTML `<table>` 或轻量矩阵组件即可（行数=故事/任务数，列数=模块数，两者规模都远小于任务依赖图的节点数）。数据源：`affected_modules` 字段（技术宪法方案的既有产出），无需新增数据。依赖技术宪法方案的 Story/Task `affected_modules` 落地后才有数据可展示，本设计的这部分是消费端，不阻塞技术宪法本身的实现。

## 5. ADR 演进时间线

### 5.1 为什么是时间线，不是图

`AdrRecord.supersedes` 是单向引用（新决策指向被替代的旧决策），链条本质是历史序列，不是网络关系——用户想问的是"架构是怎么一步步演变到今天的"，时间线（按 `seq` 排序的纵向/横向轴，每个 ADR 是一个节点，`supersedes` 用虚线连接被替代者）比图更直接地回答这个问题。里程碑锚点（`milestone.adr_id`）作为时间线上的标记点叠加显示（"这是 v0.2 发布时的架构状态"）。

### 5.2 落点

这部分与 `technical-constitution.md` §7 已经规划的"Web 端技术宪法页面"直接相关——时间线是"ADR 历史"这个既有故事（技术宪法旅程第 8 条故事）的具体呈现方式，不需要新增独立故事，实现时并入该故事即可。

## 6. 实现顺序建议

1. **Task 依赖图**（§3）——独立可做，不依赖技术宪法方案，直接回应"任务过多不好管理"的当下诉求，且是启用已装三周的孤儿依赖，优先级最高。
2. **模块归属矩阵**（§4）——依赖技术宪法方案里 Story/Task 的 `affected_modules` 字段先落地（故事「xcart adr 子命令与 story/task 模块归属标注」），矩阵组件本身很轻量。
3. **ADR 演进时间线**（§5）——并入技术宪法方案既有的 Web UI 故事，不单独排期。

## 7. 风险

1. **`@dagrejs/dagre` 版本核实**：`package.json` 声明 `^3.0.0`，实现前需确认锁定版本（`bun.lock`）与 API 是否匹配当前 dagre 3.x 的调用方式（3.x 相对 2.x 有 API 变化），避免"依赖存在但版本不对"这个新坑。
2. **依赖数据的准确性**：任务依赖图的价值完全取决于 `Task.dependencies` 数据本身是否准确维护——如果任务创建时依赖关系没被认真填写，图再好看也没有信息量。这是数据治理问题，不是可视化设计能解决的，值得在推广这个视图时提醒用户。
3. **矩阵规模上限**：模块数量如果远超故事/任务数量（现实中不太可能，但需要在实现时加一个合理性检查），矩阵会转向"列多行少"的反向拥挤，届时需要转置或分页，不在本次范围内处理。
