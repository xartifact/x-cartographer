## 🏗️ 架构概览

### 设计原则

1. **AI Native 优先**: 所有核心功能围绕 LLM 能力设计
2. **Bulletproof React 规范**: 遵循功能模块化、关注点分离
3. **类型安全**: 全面使用 TypeScript，避免 any
4. **性能优先**: 考虑大规模数据可视化性能
5. **可扩展性**: 支持未来功能扩展和多 LLM 提供商

### 技术架构图

```
┌─────────────────────────────────────────────────────────────┐
│                      用户界面层 (UI Layer)                    │
│  Next.js App Router + React 18 + Tailwind CSS               │
├─────────────────────────────────────────────────────────────┤
│                    状态管理层 (State Layer)                   │
│  Zustand (全局状态) + React Query (服务器状态)               │
├─────────────────────────────────────────────────────────────┤
│                    业务逻辑层 (Logic Layer)                   │
│  Features: Requirements | StoryMap | Tasks | Settings       │
├─────────────────────────────────────────────────────────────┤
│                    服务层 (Service Layer)                     │
│  LLM Client | TOML Parser | Storage Manager                 │
├─────────────────────────────────────────────────────────────┤
│                    数据层 (Data Layer)                        │
│  localStorage + TOML Files (导入/导出)                       │
└─────────────────────────────────────────────────────────────┘
         ↓                    ↓                    ↓
   OpenAI API          Anthropic API         Future LLMs
```

### 目录职责说明

#### 📱 `src/app/` - App Router
- **职责**: 定义路由、页面布局、服务端组件
- **原则**: 仅包含路由定义和页面组装，业务逻辑在 features 中

#### 🧩 `src/components/` - 共享组件
- **职责**: 跨功能模块复用的 UI 组件
- **原则**: 无业务逻辑，高度可复用

#### ⚙️ `src/features/` - 功能模块
- **职责**: 核心业务功能，包含组件、逻辑、状态
- **原则**: 按功能垂直切分，每个模块自包含

#### 🛠️ `src/lib/` - 工具库
- **职责**: 与框架无关的工具函数和服务
- **原则**: 纯函数，可独立测试

#### 📦 `src/types/` - 类型定义
- **职责**: 全局共享的 TypeScript 类型
- **原则**: 保持类型定义和实现分离

## 🎯 核心技术栈选型

### 框架与运行时

| 技术 | 版本 | 选择理由 | 替代方案 |
|------|------|----------|----------|
| **Next.js** | 15.x | • App Router 支持 RSC<br>• 优秀的 SSR/SSG 性能<br>• 开箱即用的路由和 API<br>• Vercel 部署便捷 | Remix, Vite + React Router |
| **React** | 18.x | • 成熟的组件生态<br>• Server Components<br>• Concurrent Features | Vue, Svelte |
| **TypeScript** | 5.x | • 类型安全<br>• 更好的开发体验<br>• 减少运行时错误 | Flow, JSDoc |
| **Node.js** | 20 LTS | • 稳定性和长期支持<br>• Next.js 官方推荐 | Bun, Deno |

### UI 与样式

| 技术 | 版本 | 选择理由 | 替代方案 |
|------|------|----------|----------|
| **Tailwind CSS** | 3.x | • 快速开发<br>• 高度可定制<br>• 优秀的 Tree-shaking<br>• 与 Next.js 无缝集成 | CSS Modules, Styled Components |
| **shadcn/ui** | 最新 | • 基于 Radix UI + Tailwind<br>• 组件代码在项目中，完全可控<br>• 优秀的 TypeScript 支持<br>• 丰富的组件库<br>• 无障碍性内置 | Radix UI, Headless UI, Ariakit |

## 💡 关键技术决策

### 决策 1: 为什么选择 React Flow 而不是自己实现 Canvas?

**选择**: React Flow

**理由**:
1. ✅ 开箱即用的缩放、平移、拖拽
2. ✅ 自定义节点和边的能力
3. ✅ 性能优化（虚拟化渲染）
4. ✅ TypeScript 支持完善
5. ✅ 活跃的社区和文档

**权衡**:
- ❌ 包体积较大 (~200KB)
- ✅ 但节省大量开发时间，值得

### 决策 2: 为什么选择 Zustand 而不是 Redux?

**选择**: Zustand

**理由**:
1. ✅ 极简 API，学习曲线平缓
2. ✅ 无需 Provider 包裹
3. ✅ 包体积小 (1KB vs 45KB)
4. ✅ 适合本项目中小型状态管理需求
5. ✅ 与 React 18 并发特性兼容

**权衡**:
- ❌ Redux DevTools 支持较弱（但有社区插件）
- ✅ 对于 MVP 足够

### 决策 3: 为什么使用 TanStack Query 处理 LLM 调用?

**选择**: TanStack Query (React Query)

**理由**:
1. ✅ 自动缓存，减少 API 调用成本
2. ✅ 请求去重（多次点击同一按钮）
3. ✅ 自动重试和错误处理
4. ✅ 乐观更新支持
5. ✅ SSR 友好

**权衡**:
- ❌ 学习曲线（但文档优秀）
- ✅ 长期收益巨大

### 决策 4: 为什么使用 localStorage 而不是数据库?

**选择**: localStorage (MVP 阶段)

**理由**:
1. ✅ 零后端成本
2. ✅ 快速 MVP 验证
3. ✅ 用户数据完全本地化（隐私）
4. ✅ 离线可用
5. ✅ 导出/导入机制补充

**未来迁移路径**:
- Phase 2: 添加可选的云存储（Supabase/Firebase）
- Phase 3: 团队协作需要后端

### 决策 5: 为什么选择 Vercel AI SDK 而不是直接调用 API?

**选择**: Vercel AI SDK

**理由**:
1. ✅ 统一多个 LLM 提供商接口
2. ✅ 内置流式响应支持
3. ✅ React Hooks 开箱即用
4. ✅ Edge Runtime 优化
5. ✅ 与 Next.js 深度集成

**权衡**:
- ❌ 增加一层抽象
- ✅ 但提供更好的开发体验和可维护性

### 决策 6: 为什么选择 shadcn/ui?

**选择**: shadcn/ui

**理由**:
1. ✅ 基于 Radix UI（无障碍性）+ Tailwind CSS
2. ✅ 组件代码直接在项目中，完全可控和可定制
3. ✅ 不是 npm 依赖，避免版本锁定
4. ✅ 优秀的 TypeScript 支持和类型推导
5. ✅ 丰富的组件库（40+ 组件）
6. ✅ 活跃的社区和持续更新
7. ✅ 与 Next.js 深度集成
8. ✅ 内置暗色模式支持

**权衡**:
- ✅ 组件在项目中，易于定制和修改
- ✅ 学习曲线平缓，文档优秀
- ✅ 适合快速构建生产级应用

### 决策 7: 为什么不使用测试框架?

**决策**: MVP 阶段不写单元测试

**理由**:
1. ✅ 快速 MVP 验证
2. ✅ 产品需求可能快速变化
3. ✅ 优先保证核心功能实现

**未来计划**:
- Phase 2: 添加关键功能的集成测试
- Phase 3: 完善单元测试覆盖
